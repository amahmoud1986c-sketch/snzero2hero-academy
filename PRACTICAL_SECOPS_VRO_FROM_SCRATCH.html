§5 — PDI lab steps (SOC analyst + implementer)

Lab path — ~90 minutes on a fresh PDI

Activate plugins → seed CMDB → import sample finding → verify master/VI → assignment rule → Flow notification → remediation change → close VI.

Lab A — Enable SecOps stack

  1. Open VR + SIR + TI + CTD plugins; activate (PDI may take several minutes).
  2. Run Guided Setup SecOps/Vulnerability tiles until green checks (groups, properties, sample data if offered).
  3. Create groups: Vulnerability Managers, Unix Admins, Windows Admins via Groups; assign test users.
  4. Confirm roles: e.g. sn_vul.vulnerability_read, sn_vul.vulnerability_write (names vary by version — search role list).

Lab B — CMDB anchor (before scan data)

  1. Create or pick two servers in cmdb_ci_server; set name, ip_address, business_criticality.
  2. Note FQDN/IP — import transform will match on these keys.
  3. Optional: open IRE identifiers and trace which fields identify a Linux server.

Lab C — Simulate scanner import

  1. Locate VR import set table (often vendor-specific staging) via tables sn_vul% or use OOB sample import if Guided Setup loaded one.
  2. Load 2 rows: same CVE, two different hostnames matching your CIs.
  3. Run transform; open Vulnerabilities — expect one master.
  4. Open Vulnerable Items — expect two VIs with CI populated.
// Optional: adjust risk on a VI (Background script)
var vi = new GlideRecord('sn_vul_vulnerable_item');
vi.addQuery('state', 'open');
vi.setLimit(1);
vi.query();
if (vi.next()) {
  vi.setValue('priority', '1');
  vi.update();
  gs.info('Updated ' + vi.number);
}

Lab D — Assignment rule

  1. Open Assignment rules; New.
  2. Condition: CI class = Linux Server OR tag = production.
  3. Action: Assignment group = Unix Admins.
  4. Re-import or update VI; confirm group changed on form.

Lab E — Analyst workflow (workspace)

  1. Open VR workspace as vulnerability manager.
  2. Filter open P1; open one VI; review linked CVE master and solution.
  3. Create Change Request (category security); link from VI related lists.
  4. Move VI to In progress; set planned remediation date.

Lab F — Close loop

  1. Simulate rescan: update VI state to Closed with close code Fixed (or import absent row per OOB logic).
  2. Verify master still shows correct open VI count.
  3. Document SLA: compare opened vs closed timestamps on VI.

Lab G — Cross-app (optional 30 min)

  1. Create TI indicator on sn_ti_indicator; relate to SIR test incident.
  2. Run one CTD test from CTD tests; observe failing CI → VI pattern if configured.
  3. Open SIR workspace; confirm shared CI appears on both SIR and VI.

§6 — Best practice chips (VR / SecOps)

✓ Activate VR+CMDB before scanner spokes ✓ IRE match keys = scanner export fields ✓ One CVE master, many VIs ✓ Assignment rules before go-live import ✓ P1/P2 SLA defined per priority band ✓ Remediate via change for prod CIs ✓ Use VR workspace for owners, not raw lists ✓ Flow Designer for notify + auto-assign ✓ Separate SecOps groups from ITSM admin ✓ Test import on subset staging first ✓ Link VI to cmdb_ci always ✓ Deferral = risk approval workflow ✗ Close VI with open exploit on critical CI ✗ Duplicate CVE masters per scanner ✗ Global scope custom VR tables ✗ Manual assign 10k VIs ✗ Skip rescan verification ✗ Patch without change on prod ✗ Mix SIR playbooks into VR flows blindly ✗ Table API bulk load without transform ✗ Admin-only UAT (use owner persona) ✗ Rewrite OOB sn_vul transforms in global ✗ Ignore third-party exploit intel feed

  1) Lookup assignment_group (from CI.support_group or assignment rule output)
  2) Update Record (VI.assignment_group, VI.state = in_progress)
  3) Create Record change_request (short_description, cmdb_ci, category=security)
  4) Create Record task_ci (link CI to change if needed)
  5) Send Notification (template: include VI.number, CVE, CI name, {BASE} link)

Do: Keep OOB VR flows active; add **new** flows for customer-specific notify/ITSM integration. Use subflows for "create change" so SIR and VR can reuse.

Don't: Clone and edit vendor-owned global flows in production without update set discipline — prefer extension flows triggered on same table with order/conditions that complement OOB.

§8 — ServiceNow SDK: CAN vs CANNOT for VR/SecOps

See full toolchain: SDK_CURSOR_FULL_DOCUMENTATION.html · SDK Windows full cycle · Flow labs: PRACTICAL_FLOW_DESIGNER_FROM_SCRATCH.html · events: 06_NOTIFICATIONS_EVENTS_JOBS.html.

SDK CAN

  • Custom **scoped app** wrappers around VR APIs (Script Includes, REST)
  • Fluent Flow (where supported) for remediation automation in your scope
  • Record() metadata for **your** tables, properties, roles in scope
  • ATF tests that assert VI state transitions in PDI
  • Integration outbound from scoped app to ticketing/SOAR
  • Custom notifications referencing VI fields via mail scripts in scope

SDK CAN (config)

  • Export/update sets for scoped artifacts only
  • CI/CD pipeline for scoped application code
  • Scripted REST facade: accept scanner JSON → call OOB API
  • Custom dashboards/widgets reading sn_vul_vulnerable_item (read ACLs)
  • Wrapper SI: prioritize() pattern in scoped include calling GlideRecord

SDK CANNOT

  • Redefine or patch **OOB** sn_vul store apps/plugins via SDK
  • Replace **scanner IntegrationHub spoke** UI or closed vendor actions
  • Ship **Playbook Designer / Workflow Studio** graphs from SDK repo
  • Alter CMDB IRE OOB identifiers as scoped Fluent records (use instance config)
  • Clone VR workspace UX components as unsupported overrides
  • Grant cross-scope VR admin without platform governance

Appendix — Scanner integration checklist

  • Connection credentials in IH Connection (mid-server if on-prem scanner).
  • Spoke actions scheduled via Scheduled job or vendor pull frequency.
  • Transform errors: Import set runs → error rows.
  • Duplicate VI prevention: OOB dedupe on CI + vulnerability; do not disable without design.
  • Post-import: run VR prioritization job if enabled (check Jobs named Vulnerability).

Appendix — Vulnerability groups (bulk remediation)

Group VIs by host, application, or patch ID to open one change for many items. Search lists/filters on VI for shared vulnerability.patch_id or business service. Pattern documented in SECOPS.html §4.5.

// Bulk change pattern (background — adapt thresholds)
var agg = new GlideAggregate('sn_vul_vulnerable_item');
agg.addQuery('state', 'open');
agg.addQuery('priority', 'IN', '1,2');
agg.addAggregate('COUNT');
agg.groupBy('vulnerability.patch_id');
agg.query();
while (agg.next()) {
  var patchId = agg.getValue('vulnerability.patch_id');
  var count = parseInt(agg.getAggregate('COUNT'), 10);
  if (patchId && count >= 5) {
    gs.info('Consider bulk CHG for patch ' + patchId + ' (' + count + ' VIs)');
  }
}
