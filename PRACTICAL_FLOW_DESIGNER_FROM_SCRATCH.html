§1 — When to use Flow Designer vs Business Rule vs Fluent Flow()

At a glance — pick one primary tool

Business Rule

Same-transaction field defaults, sync validation, thin “set value before insert”. Keep short. No multi-step approvals.

Flow Designer (UI)

Approvals, multi-step, spokes, notifications, wait conditions, visible to process owners. First choice for new automation.

Fluent Flow()

Same WFA artefact as code for CI/CD. Build in UI first if complex, then transform — or author Fluent when team owns SDK.

Use Business Rule when…

  • Must run in the same DB transaction
  • Set u_approver_user before save (HR Leave BR1)
  • Abort invalid insert with current.setAbortAction(true)

Use Flow Designer when…

  • Ask for Approval / wait for answer
  • Create Change + notify + update VI
  • IntegrationHub spoke actions
  • Non-developers must read the process

Use Fluent Flow() when…

  • App is already SDK-first
  • You need reproducible install across instances
  • You transform UI flows into source of truth
✓ BR for sync field math · Flow for process ✓ One owner per process (avoid BR + Flow both updating state) ✗ Long Glide loops inside BR that should be Flow + For Each ✗ Duplicate approval logic in Script Include and Flow

HR Leave rule: requests are often created as draft then updated to submitted — use Record Updated with condition u_state = submitted (and previous ≠ submitted if available).

VR rule: VI can be created by import in bulk — prefer Updated when priority/state crosses a threshold, or Created with assignment empty, so you do not double-fire.

§9 — Best practices (Do / Don't)

✓ Name flows with app prefix (HRLX / VR) ✓ Tight trigger conditions before Activate ✓ One writer of each state field ✓ Test with impersonation + flow context ✓ Prefer Subflow for repeated blocks ✗ gs.print debugging left in production actions ✗ Flow + BR both flipping the same state ✗ Unbounded For Each on full VI table ✗ Activate on prod without sub-prod soak

§10 — SDK side: what Flow() can and cannot do

CAN: Define Workflow Automation flows in Fluent (Flow() / WFA APIs); ship with build + install; activate on install unless --skip-flow-activation; pull UI-built flows with npx @servicenow/sdk transform --table sys_hub_flow --auth DEV; author subflows and reusable actions where APIs exist; study offline with npx @servicenow/sdk explain flow-api and explain wfa-flow-guide.

CANNOT: Replace Flow Designer’s live data-pill picker / design-time UX; debug mid-canvas with live record pills from the CLI; own every playbook / experience-only activity via Fluent; assume install merges gently — it deploys your app package (coordinate so you do not wipe teammates’ unpublished UI-only edits). Runtime VI/user data is not in the Fluent package.

# Windows PowerShell — after UI flow is stable
cd C:\SVCProject\HR_Leave_App\servicenow-ai-workspace\hr-leave-sdk
npx @servicenow/sdk explain flow-api
npx @servicenow/sdk explain wfa-flow-guide
npx @servicenow/sdk transform --table sys_hub_flow --auth DEV
npx @servicenow/sdk build
npx @servicenow/sdk install --auth DEV
# Optional: do not auto-activate flows
