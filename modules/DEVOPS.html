1) Overview & Business Value

Open component:ApplicationLeave Requests

DevOps Change Velocity connects pipelines to ITSM so every build, test, and deploy is recorded as governed change. — هي الطبقة التي تجعل البايبلاين يفتح ويغلق Change Request تلقائيًا بدلاً من النموذج اليدوي.

Why customers buy it:

  • Reduce mean change lead time from days to minutes by automating Standard Changes.
  • اختصار زمن التغيير وتحويل الطلبات المتكرّرة إلى موافقات تلقائية.
  • Provide auditable trail (SOX, ISO 27001, ITIL) — every artifact tied to a CR, every CR tied to a CI.
  • إثبات للمراجع: كل نشر معروف من أين جاء، من وافق عليه، وماذا غيّر.
  • Surface DORA metrics (Deployment frequency, Lead time, Change failure rate, MTTR) at executive level.
  • مؤشرات DORA الأربعة جاهزة من Performance Analytics دون استخراج يدوي.
  • Reduce change failure rate via gates: code quality (SonarQube), security (Snyk/Veracode), test coverage.
  • بوابات قبل النشر تمنع التغييرات الخطرة من الوصول للإنتاج.
  • Connect deployments to incidents and CIs through Service Graph for blast-radius awareness.
  • ربط كل نشر بالخدمة المتأثرة لمعرفة من سيتألم لو فشل.

Business outcomes (typical 12-month):

  • 60–80% of CRs become Standard auto-approved (was 0–15%).
  • 25–40% reduction in change failure rate.
  • 30–50% faster MTTR (because deploy → incident link is instant).
  • Audit prep drops from weeks to hours.

⚠️ DevOps is not a replacement for Change Management — it accelerates it. Governance still applies.

5) End-to-End Process Cycle

Open component:ApplicationLeave Requests

The full pipeline → ITSM cycle:

Commit (developer)
 → SCM webhook to DevOps (sn_devops_commit row)
 → Build (Jenkins/GitHub Actions step → sn_devops_step_execution)
 → Test (JUnit/Cypress → sn_devops_test_result)
 → Code quality (SonarQube → sn_devops_security_result)
 → Security scan (Snyk/Veracode → sn_devops_security_result)
 → Artifact published (sn_devops_artifact_version)
 → Change Request (sn_devops_change_request → change_request)
 ├─ Standard? auto-approve via policy
 └─ Normal? CAB workflow
 → Deploy step blocked until CR approved
 → Deploy (artifact → cmdb_ci)
 → Verify (smoke tests, health checks)
 → Close CR (auto from pipeline)
 → Monitor (incidents linked back)
 → Feedback (Insights: DORA + change failure rate)

دورة كاملة من commit حتى مراقبة الإنتاج — كل خطوة لها سجلّ.

6) Development — Custom Step Definitions & Tools

Open component:Application FilesScripts portal

Custom step types (for tools without out-of-box spoke):

// Script Include: CustomDevOpsStepHandler
var CustomDevOpsStepHandler = Class.create();
CustomDevOpsStepHandler.prototype = {
 initialize: function() {},

handleStepStart: function(payload) {
var step = new GlideRecord(‘sn_devops_step_execution’);
step.initialize();
step.pipeline_execution = payload.pipelineExecutionId;
step.tool = payload.toolId;
step.name = payload.stepName;
step.state = ‘in_progress’;
step.start_time = new GlideDateTime();
step.external_id = payload.externalId;
step.external_url = payload.url;
return step.insert();
},

handleStepEnd: function(payload) {
var step = new GlideRecord(‘sn_devops_step_execution’);
if (step.get(‘external_id’, payload.externalId)) {
step.state = payload.success ? ‘success’ : ‘failed’;
step.end_time = new GlideDateTime();
step.output = payload.output;
step.update();
}
},

type: ‘CustomDevOpsStepHandler’
};

Register a custom tool (Argo CD example):

var tool = new GlideRecord('sn_devops_tool');

tool.tool_type = 'orchestration';

gs.info('Argo tool sys_id: ' + sysId);

Inbound REST handler (custom webhook):

// Scripted REST resource: /api/x_acme/devops/argo
(function process(request, response) {
 var body = request.body.data;
 var handler = new CustomDevOpsStepHandler();
 if (body.event === 'sync_started') {
 handler.handleStepStart({
 pipelineExecutionId: body.pipelineExecutionId,
 toolId: body.toolId,
 stepName: 'Argo Sync ' + body.app,
 externalId: body.syncId,
 url: body.argoUrl
 });
 } else if (body.event === 'sync_completed') {
 handler.handleStepEnd({
 externalId: body.syncId,
 success: body.status === 'Synced',
 output: body.message
 });
 }
 response.setStatus(200);
})(request, response);

9) Best Practices & Common Mistakes

Open component:ApplicationLeave Requests

Best practices:

  • Start with one team and one pipeline; expand by team, not by feature.
  • ابدأ بفريق واحد، لا تحاول تغطية الجميع من اليوم الأول.
  • Map every pipeline to an Application Service in CMDB before turning on auto-CR.
  • اربط كل بايبلاين بخدمة CMDB قبل تفعيل الـ CR التلقائي.
  • Define Standard Change templates with explicit guardrails (tests, security, coverage).
  • اشترط بوّابات اختبار + كود كوفر + فحص أمان قبل اعتبار التغيير Standard.
  • Use Service Graph to compute blast radius — surface in CR risk score.
  • استخدم Service Graph ليعرف Risk Score الفئة المتأثرة.
  • Run DORA quarterly review with engineering leadership.
  • اجتماع ربعي يعرض DORA على القيادة الهندسية.

Common mistakes:

  • Treating every pipeline as Normal CR — kills velocity gain.
  • اعتبار كل تغيير Normal CR — يلغي الفائدة من الأتمتة.
  • Forgetting to rotate webhook secrets — security finding waiting to happen.
  • نسيان تدوير أسرار الويب هوك — ثغرة أمنية مؤكدة في المراجعة.
  • Pushing pipeline data without CMDB mapping — CRs orphaned from CIs.
  • إدخال البايبلاين دون ربط CMDB — CR بدون CI = لا تتبّع تأثير.
  • Letting sn_devops.integration_user get admin — over-privileged service account.
  • منح المستخدم التكاملي صلاحيات أكثر من اللازم — أكبر خطأ أمني شائع.
  • Allowing both ServiceNow and Jira to be source of truth — pick one master.
  • ازدواج مصدر الحقيقة بين Jira و ServiceNow — اختر واحدًا.

⚠️ A CR without a CI link is a CR you cannot audit. Block at policy level.
